## 1. 결론 먼저

1. **도구는 이미 충분하다.** 7개 도구의 커버리지와 설명 품질(언제 다른 도구를 써야 하는지, JSON 스키마, 실데이터 분포)은 이미 상위권이다. 여기에 도구를 더 얹는 것은 효익이 낮다.
2. **병목은 데이터 신선도의 불투명성이다.** 토픽 클러스터는 전체 법안의 5%만 덮고 2026-03 이후 발의 법안은 0% 배정인데, 도구는 "법안군 278개"라고 말한다. 처리 상태는 0% 채워져 있는데 도구는 그 사실을 아예 언급하지 않는다. 에이전트는 이를 알 방법이 없어 **자신 있게 틀린 답**을 만든다.
3. **따라서 1순위는 신규 기능이 아니라 (a) 서버가 자기 한계를 런타임에 말하게 만드는 것, (b) 데이터 축을 "발의"에서 "처리"까지 넓히는 것이다.**

## 3. 진단

### D1 — 조용한 노후화 (토픽 클러스터)

`bills_topics` 는 "법안군 278개"를 내세우지만 실제로는 전체의 5%(993건)만 묶여 있고, **2026-03 이후 발의된 약 3,300건은 단 한 건도 배정되지 않았다.** 클러스터 자체도 2026-06-22 이후 새로 만들어지지 않았다.

"지금 국회에서 어떤 주제가 뭉쳐 있나"라는 질문에 이 도구는 6개월 전 스냅샷을 현재인 것처럼 답한다. 도구 설명·응답 어디에도 커버리지 표기가 없어 에이전트가 보정할 수 없다. **틀린 답보다 나쁜 것은 한계를 모른 채 확신하는 답이다.**

### D2 — 생애주기 공백 (처리 상태)

이 서버는 "국회가 무엇을 제안했는가"만 답한다. "그래서 통과됐는가"에는 답하지 못한다. `bills_monitor_bills.status` 컬럼은 존재하지만 20,035건 전부 비어 있다.

데이터가 없어서가 아니다. `bills_raw_data.raw_json` 에 국회 API의 `STATUS` 필드가 실재하며 실제 값 분포도 확인된다 — 대안반영폐기 678, 원안가결 205, 수정가결 72, 철회 51, 폐기 2. `CMT_PRESENT_DT`(위원회 상정일) 5,330건, `LAW_PRESENT_DT`(법사위 회부일) 467건도 이미 수집돼 있다. **수집 경로는 검증됐고 2026-02에 파이프라인이 멈췄을 뿐이다.**

### D3 — 프로토콜 표면 미활용

모든 응답이 단일 text 블록이다. MCP의 `structuredContent`/`outputSchema`, `prompts`, `resources`, `completions` 를 하나도 쓰지 않는다. 결과:

- 도구 설명에 JSON 스키마를 **문자열로** 적어두고 에이전트가 텍스트에서 파싱하게 한다. 기계 판독 가능한 형태로 승격할 재료가 이미 다 있다.
- 위원회명·의원명·정당명 자동완성이 없어 표기 오타가 곧 0건 응답이 된다.
- "주간 입법 브리핑" 같은 반복 워크플로를 매번 에이전트가 도구 조합으로 재발명한다.

### D4 — 설명 수치의 고착

도구 설명의 분포 수치(`economic 7856건` 등)가 **19,999건 시점 스냅샷에 하드코딩**돼 있다. 현재 실측은 economic 7,873 / social 7,154 / administrative 2,867 / political 1,834 / environmental 203 / cultural 104 로 이미 드리프트가 시작됐다.

수치 자체의 오차는 아직 작지만, **수동 갱신에 의존하는 구조는 D1과 정확히 같은 방식으로 실패한다.**

## 7. 하지 않을 것

- **도구 개수 늘리기.** 7개로 질문 공간을 이미 덮는다. `bills_search`/`bills_filter` 경계 혼동이 이미 관리 대상인데 표면을 더 넓히면 악화된다. P1의 경과 조회는 예외 — 새 질문 유형이라 기존 도구에 끼워 넣을 자리가 없다.
- **쓰기 기능.** 읽기 전용은 제약이 아니라 이 서버의 신뢰 근거다.
- **공동발의자 추정·보간.** 원문에 이름이 없다. 추정으로 채우면 조용한 오답이 된다. 8절 H1의 검증 결과가 나오기 전까지는 손대지 않는다.
- **임베딩 모델 교체.** 커버리지 100%, 검색 품질에 대한 불만이 계측된 바 없다. 비용 대비 효익이 없다.
- **클러스터링 알고리즘 개선을 P0에 올리기.** 배정률이 0%인 구간에서 품질을 손보는 것은 순서가 틀렸다. 커버리지 복구가 먼저다.

## 9. 이 문서를 다시 읽을 때

여기 적힌 수치는 2026-08-15 직접 조회 결과다. 데이터는 매일 쌓이므로 **판정(정상/정지/공백)만 신뢰하고 절대 수치는 다시 측정하라.** 특히 P0 착수 전에 클러스터 배정률과 `status` 커버리지를 재확인해야 한다. 그 사이 파이프라인이 복구됐다면 이 전략의 우선순위 자체가 바뀐다.
