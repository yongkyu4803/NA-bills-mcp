## 0. v1 을 폐기하는 이유

v1 은 두 가지를 **고장**으로 봤다. 둘 다 고장이 아니었다.

| v1 의 판정 | 실제 |
|---|---|
| "처리 상태가 0% 다 → 파이프라인이 멈췄다" | 원래 안 모은다. 법안은 **발의되는 순간 한 번** 수집되고, 그 뒤 심사·처리 경과는 추적하지 않는 것이 설계다. |
| "토픽 클러스터가 5% 다 → 방치됐다" | 원래 **사람이 손으로** 묶는다. 5% 는 방치의 결과가 아니라 선별의 결과다. |

전제가 바뀌면 결론도 바뀐다. v1 의 핵심 제안이던 "처리 상태 수집 재가동"은 통째로 사라지고,
"클러스터 배정률 90% 달성"은 애초에 달성할 수 없는 목표가 된다.

## 1. 이 서버는 무엇인가 (한 문장)

> **제22대 국회에 어떤 법안이 발의됐는지**를 알려주는 서버다.
> **그 법안이 어떻게 됐는지**는 알려주지 않는다.

이 한 줄이 이 문서 전체의 기준이다. 앞줄은 잘한다. 뒷줄은 못 하는 게 아니라 **안 하기로 한 것**이다.

---

## 2. 진짜 문제 하나

기능이 부족한 게 아니다. 문제는 딱 하나다.

> **서버가 자기 경계를 말하지 않는다.**

에이전트(LLM)는 도구 설명에 적힌 것만 안다. 지금 도구 설명에는
"처리 상태는 제공하지 않는다", "토픽은 일부만 수동으로 묶은 것이다" 라는 말이 **한 줄도 없다.**

그래서 이런 일이 생긴다.

| 사용자 질문 | 지금 벌어지는 일 |
|---|---|
| "이 법안 통과됐어?" | 서버가 답이 없다고 말하지 않으니, 에이전트가 요약문을 읽고 **추측해서** 답한다 |
| "요즘 어떤 주제가 많이 발의돼?" | `bills_topics` 가 "법안군 278개"라고 하니 그대로 답한다. 실제로는 2026-03 이후 법안이 하나도 안 들어간 6개월 전 선별 결과다 |

**틀린 답보다 나쁜 것은, 한계를 모른 채 확신하는 답이다.**
데이터를 더 모으지 않아도, 이건 지금 당장 고칠 수 있다.

## 4. 할 일

우선순위 원칙: **잘못된 답을 막는 게 먼저, 편하게 만드는 건 그다음.**

### P0 — 경계를 말하게 하기 (작은 변경, 큰 효과)

이건 임시방편이 아니라 **영구적인 인터페이스 계약**이다. 나중에 데이터가 늘어도 안 걷어낸다.

| # | 할 일 | 왜 |
|---|---|---|
| 0-1 | 모든 도구 설명 맨 앞에 한 줄 넣기 — "이 서버는 **발의 시점 정보**만 제공한다. 심사·처리 경과는 없다." | 에이전트가 읽는 유일한 스펙이 도구 설명이다 |
| 0-2 | 처리 상태 질문에 쓸 **표준 안내 문구** 만들기 — 못 한다고 말하고, 의안정보시스템 원문 링크로 보낸다 | 침묵하면 에이전트가 추측한다. "대신 무엇을 하라"까지 줘야 한다 |
| 0-3 | `bills_topics` 설명을 고치기 — "전체 분류"가 아니라 **"사람이 손으로 묶은 하이라이트 모음"**. 마지막 갱신일도 같이 노출 | 성격 자체를 잘못 알리고 있다. 커버리지 숫자만 붙이는 걸론 부족 |
| 0-4 | "요즘 무슨 주제가 많나" 류 질문은 `bills_filter` / `bills_statistics` 로 가라고 도구 설명에 명시 | 0-3 만 하면 에이전트가 갈 곳을 잃는다 |
| 0-5 | `status` 컬럼과 상태 관련 필드를 응답에서 **아예 빼기**. 코드에 "왜 안 쓰는지" 주석 남기기 | 빈 칸이 나가면 "아직 미정"으로 오해된다. 주석이 없으면 6개월 뒤 누군가 "이거 채우면 되겠네" 하고 되돌아온다 |
| 0-6 | 응답에 데이터 기준일(`data_as_of`) 붙이기 | 언제 기준 데이터인지 에이전트가 알아야 보정할 수 있다 |

**됐는지 어떻게 아나**: MCP 클라이언트로 "이 법안 통과됐어?", "요즘 어떤 주제가 뭉쳐 있어?" 를 물어본다.
에이전트가 **스스로 한계를 말하면** 성공이다. `evaluation.xml` 에 이 두 질문을 추가한다.

### P1 — 쓰기 편하게 (MCP 기능 활용)

지금은 MCP 프로토콜 기능을 거의 안 쓴다. 응답이 전부 텍스트 한 덩어리다.

| # | 할 일 | 효과 |
|---|---|---|
| 1-1 | `structuredContent` + `outputSchema` — 지금은 JSON 스키마를 **설명에 글로 적어놓고** 에이전트더러 파싱하라고 한다. 기계가 읽는 형태로 승격 | 파싱 오류 감소 |
| 1-2 | `completions` — 위원회명·의원명·정당명 자동완성 | 지금은 오타 하나면 그냥 0건. 원인도 안 알려준다 |
| 1-3 | `prompts` — "주간 입법 브리핑", "의원 활동 요약" 같은 반복 작업을 미리 만들어두기 | 매번 에이전트가 도구 조합을 재발명한다 |
| 1-4 | `resources` — 일일 리포트를 `bills://report/{date}` 로 노출 | 이미 506건 쌓여 있는데 도구로만 접근 가능 |
| 1-5 | 도구 설명 속 통계 수치를 빌드할 때 DB 에서 자동 생성 | 지금은 19,999건 시점 숫자가 하드코딩. 손으로 갱신하는 구조는 반드시 낡는다 |

### P2 — 다시 안 틀어지게

| # | 할 일 |
|---|---|
| 2-1 | `evaluation.xml` 자동 실행 러너 — 배포 전에 회귀 잡기 (지금은 테스트가 아예 없다) |
| 2-2 | 도구 호출 계측 — 0건 응답률, 오류율, 도구별 사용 분포 (개인정보 없는 집계만) |
| 2-3 | 요청 제한을 공유 저장소(Upstash 등)로 교체 — 지금은 인스턴스 메모리라 여러 개 뜨면 무력화 |
| 2-4 | 토픽 클러스터 **최종 갱신일**을 헬스체크에 표기 |

⚠️ 2-4 는 **알람 임계치로 잡으면 안 된다.** 수동 운영이라 늘 낮게 나오고, 영원히 울리는 알람은 곧 무시된다.
"지금 며칠 전 데이터인지" 보여주는 정보 표시로만 쓴다.

## 5. 아직 정해야 할 것

### 결정 1 — 이 서버를 더 깊게 만들 것인가?

처리 상태가 스코프 밖이면, "새로운 질문에 답한다"는 방향의 재료가 사라진다.
발의 시점 데이터 **안에서** 깊이를 찾아야 하고, 후보는 이렇다.

| 후보 | 실현성 |
|---|---|
| 중복·유사 법안 탐지 | 임베딩이 100% 라 **바로 가능** |
| 의원별 발의 패턴 분석 | 발의자 파싱이 이미 있음 |
| 21대 국회 대비 비교 | 데이터 추가 수집 필요 |

다만 "도구를 더 늘리지 않는다"는 원칙과 부딪힌다. **P1 끝난 뒤에 판단한다.**

### 결정 2 — 공동발의자를 구할 수 있나?

지금은 `proposer` 텍스트에 **대표발의자만** 있다. "등 10인"의 나머지는 알 방법이 없다.
열린국회정보 API 에 의안별 발의자 목록 엔드포인트가 있는지 확인하면 끝나는 문제다. **조사 1일.**

- 있다 → 남은 유일한 깊이 확장 카드. P1 으로 승격
- 없다 → 도구 설명에 "구조적으로 불가"라고 못 박고 영구히 닫는다

## 6. 하지 않을 것

- **처리 상태 수집.** 설계상 스코프 밖이다. 하려면 파이프라인 전체를 새로 설계해야 하고, 그건 이 문서의 범위가 아니다.
- **토픽 클러스터 자동화.** 수동 선별이 운영 방식이다. 자동화는 별개 의사결정이지 "복구"가 아니다.
- **도구 개수 늘리기.** 7개로 충분하다. `bills_search` / `bills_filter` 경계 혼동이 이미 관리 대상인데 더 늘리면 나빠진다.
- **쓰기 기능.** 읽기 전용은 제약이 아니라 이 서버의 신뢰 근거다.
- **공동발의자 추정·보간.** 원문에 이름이 없다. 추정으로 채우면 조용한 오답이 된다. 5절 결정 2 전까지 손대지 않는다.
- **임베딩 모델 교체.** 커버리지 100%, 검색 품질 불만이 계측된 적 없다. 효익 없음.

## 7. 성공 지표

| 지표 | 현재 | 목표 |
|---|---|---|
| 처리 상태 질문에 "제공하지 않는다"고 답하는 비율 | 0% (추측함) | **100%** |
| `bills_topics` 를 "선별본"으로 설명하는가 | 아니오 | 예 |
| 데이터 기준일을 노출하는 도구 | 0 / 7 | 7 / 7 |
| 평가셋 정답률 | 미측정 | 자동 측정 후 90%+ |
| 0건 응답률 | 미측정 | 측정 후 목표 설정 |

v1 에 있던 "클러스터 배정률 90%", "`status` 커버리지 95%" 는 **삭제**했다. 설계와 모순되는 목표다.
